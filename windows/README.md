# VK TURN для Windows

Тот же туннель, что на роутере и в Android-приложении (WireGuard → DTLS-SRTP → TURN-релеи звонков
VK → сервер `anton48/vk-turn-proxy -srtp`), как обычное приложение для Windows 10/11 (x64):
запустил, нажал «Включить» — работает. Три режима:

- **По доменам** (по умолчанию) — в туннель идут только сайты из списков доменов в формате
  sing-box rule-set (`.srs`) по ссылкам, например
  `https://raw.githubusercontent.com/MetaCubeX/meta-rules-dat/sing/geo/geosite/category-ai-!cn.srs`,
  и свои домены. Остальное идёт напрямую.
- **Весь трафик** — всё, кроме локальных сетей (по желанию).
- **По подсетям** — только перечисленные IPv4-подсети, как «Маршруты» в Android-приложении.

## Как пользоваться

1. Скачайте `vkturn-<версия>-windows-amd64.zip`, распакуйте куда угодно, запустите `vkturn.exe`.
2. Windows **один раз** спросит права администратора: приложение ставит себя в
   `C:\Program Files\VK TURN`, регистрирует сервис и ярлык в меню Пуск. Дальше UAC не нужен.
3. Откроется окно. Вставьте ссылку `vkturn://…` из панели сервера (`vkturn-panel`) или откройте файл
   `.vkturn` и нажмите «Импортировать и подключить». После установки ссылки `vkturn://` и файлы
   `.vkturn` открываются в приложении сами, двойным щелчком.
4. Большая кнопка включает и выключает туннель; режим — переключатель под ней. Значок в трее:
   серый — выключен, жёлтый — подключение, зелёный — работает; щелчок открывает окно, правый щелчок —
   меню.

Настройки: списки доменов и интервал их обновления (по умолчанию раз в 24 ч, и кнопка «Обновить
сейчас»), свои домены (каждый — с поддоменами), подсети, «локальные сети мимо туннеля»,
«подключаться при запуске Windows» и, в разделе «Подключение вручную», все поля Android-приложения:
сервер, ключ сервера, приватный ключ (кнопка «Новый ключ» — `vk-turn-proxyd genkey/pubkey`,
публичный показан для добавления пиром на сервер), PSK, ссылки на звонки, адрес в туннеле `/24`, DNS
в туннеле, DNS для запросов к VK, MTU, число соединений, TCP. Журнал — на отдельной вкладке.

Обновление: распакуйте новый архив и запустите его `vkturn.exe` — он заметит, что установлена другая
сборка, и (через UAC) заменит её. Удаление: `"C:\Program Files\VK TURN\vkturn.exe" uninstall`.

## Как устроено

```
vkturn.exe (пользователь)                     vkturn.exe service (SYSTEM)
 ├─ окно: Edge --app=http://127.0.0.1:47447    ├─ HTTP на 127.0.0.1:47447 (токен, cookie)
 ├─ значок в трее (Win32, без cgo)             ├─ настройки, списки .srs, журнал
 └─ первая установка через UAC                 ├─ vk-turn-proxyd.exe — дочерний процесс (job object)
                                               │    ├─ прокси: TURN, DTLS-SRTP; сокеты — IP_UNICAST_IF
                                               │    │  на физический интерфейс
                                               │    ├─ WireGuard (wireguard-go)
                                               │    └─ адаптер wintun «vkturn» (после первой сессии)
                                               ├─ адрес, MTU, метрика, маршруты — iphlpapi
                                               └─ режимы all/domains: DNS-перехватчик 127.0.0.1:53
                                                    + правило NRPT «.» → 127.0.0.1
```

Демон — тот же `cmd/vk-turn-proxyd` в «режиме приложения», что и в Android
(`network_events=stdin`): сервис пишет ему конфиг (в каталог с ACL «SYSTEM и администраторы»;
после чтения демоном удаляется), шлёт в stdin `bind <индекс>`, `network <id>`, `dns <ip>` при
смене сети и закрывает stdin для остановки. Отличие от Android — tun: на Windows его создаёт сам
демон (`tun.CreateTUN` → wintun, постоянный GUID адаптера), как на роутере; адреса и маршруты ставит
сервис, как netifd на роутере.

| Что | Роутер | Android | Windows |
|---|---|---|---|
| tun | демон | `VpnService`, fd по unix-сокету | демон (wintun) |
| адреса, маршруты | netifd | `VpnService.Builder` | сервис (iphlpapi) после первой сессии |
| свои сокеты мимо туннеля | `fwmark`/`bind_device` | uid приложения вне VPN | `IP_UNICAST_IF` на физический интерфейс (`bind_device=<индекс>`) |
| смена сети | `/proc/net/route` | `NOT_VPN`-сеть → stdin | адаптер со шлюзом и наименьшей метрикой, кроме нашего → stdin |
| остановка | SIGTERM | закрытие stdin | закрытие stdin; job object убивает демона, если сервис упал |
| `pool_reserve` | 1 | 3 | 3 (ноутбук меняет сети, как телефон) |

### Почему сервис, а не одно приложение с UAC

Адаптер, маршруты и политика DNS требуют администратора. Приложение, запускаемое с UAC, спрашивало
бы права при каждом старте и не могло бы подключиться до входа пользователя. Сервис спрашивает
один раз — при установке (так же устроен «service mode» Clash Verge). Окно и трей — процессы
пользователя без прав; они ходят к сервису по HTTP на 127.0.0.1 с токеном.

- Токен лежит в `%ProgramData%\VK TURN\ui-token`; читать его могут администраторы и пользователи,
  установившие приложение (их SID — в `ui-users`). Другой пользователь компьютера при первом запуске
  получает доступ через UAC.
- `/login?t=<токен>` ставит cookie (`HttpOnly`, `SameSite=Strict`); каждый `/api` требует cookie и
  `Host: 127.0.0.1:47447` (защита от DNS rebinding), изменения — ещё и заголовок `X-VKTurn`
  (форма или кросс-сайтовый запрос без preflight его не пошлёт). Приватный ключ из `/api` не уходит.
- Окно — Edge в режиме `--app` со своим профилем (`%LOCALAPPDATA%\VK TURN\window`): без адресной
  строки, история и расширения браузера пользователя не участвуют. Нет Edge — браузер по умолчанию.
- Почему не нативное окно: без cgo готовых GUI-библиотек нет (lxn/walk — заброшена), а страница
  уже есть и проверяется на Mac (`go run ./cmd/vkturn -demo`). Трей — 300 строк Win32 через
  `x/sys/windows`.

### Режим «по доменам»: DNS-перехватчик и /32-маршруты, а не fake-IP

Пока туннель поднят (режимы «по доменам» и «весь трафик»), все DNS-запросы Windows идут в
перехватчик на `127.0.0.1:53` (`cmd/vkturn/dns.go`):

- имя из списков → запрос уходит в DNS туннеля (`1.1.1.1` по умолчанию; ему — маршрут /32 в туннель),
  и **до** того как ответ отдан программе, каждый его A-адрес получает маршрут /32 в адаптер
  (`routes.go`). Маршрут живёт 6 ч (или 2×TTL, если больше) и продлевается каждым ответом с этим
  адресом; больше 8192 — уходит ближайший к истечению;
- AAAA, HTTPS и SVCB такого имени — пустой ответ: туннель только IPv4 (пир сервера —
  `0.0.0.0/0`), IPv6-адрес ушёл бы мимо туннеля;
- остальные имена — в DNS физической сети, сокетом, привязанным к её интерфейсу;
- `use-application-dns.net` — NXDOMAIN: канарейка Firefox, его DNS-over-HTTPS по умолчанию
  выключается;
- подсети `ip_cidr` из списков (geoip-списки) маршрутизируются целиком при подключении.

**Почему NRPT.** У адаптера можно задать свой DNS, но Windows спрашивает DNS всех адаптеров сразу
(smart multi-homed name resolution) и берёт первый ответ — провайдерский обгонял бы наш, и имя из
списка уходило бы без маршрута. Правило Name Resolution Policy Table для пространства «.» отправляет
все имена только на указанный сервер (так делают DirectAccess и интерактивный сервис OpenVPN). Ключ
правила — volatile (пропадает при перезагрузке), сервис удаляет его при остановке и при старте
(если прошлый экземпляр упал). Если в системе есть NRPT из групповой политики, локальное правило
Windows не применит — приложение скажет об этом.

**Почему не fake-IP.** Fake-IP (как в sing-box/Clash) отдаёт программам адреса из служебного
диапазона и подменяет их в пакетах: один маршрут, никакой гонки. Но для этого нужен трансляционный
слой в пути пакетов между wintun и WireGuard (перезапись адресов и контрольных сумм TCP/UDP, ICMP),
таблица соответствий, переживающая перезапуск, и фальшивые адреса в кэшах программ после выключения
туннеля. Маршруты /32 не трогают пакеты вовсе — WireGuard получает их как есть; цена — общие адреса
CDN: другой сайт на том же адресе тоже пойдёт в туннель (безвредно).

**Разбор `.srs`** (`pkg/srs`) написан по исходникам sing-box (`common/srs/binary.go`) и sing
(`common/domain`): `SRS`, версия 1…5, тело **zlib** (не zstd), правила domain/domain_suffix (LOUDS-trie
перевёрнутых имён), domain_keyword, domain_regex (RE2, как в sing-box), ip_cidr, логические and/or,
invert. Правило с условиями, которые DNS-запрос выполнить не может (port, process_name, network…),
не совпадает никогда (как и в sing-box для такого запроса); adguard_domain читается, но не
сопоставляется. Список заменяется только копией, которая разобралась; битая загрузка оставляет
старую.

### Браузеры и DNS over HTTPS

DoH браузера обходит системный DNS — имена не попадают в перехватчик, и маршрутов к ним нет.

- **Chrome / Edge**: режим «Безопасный DNS» → «Использовать текущего поставщика услуг» (автоматический)
  при наличии правил NRPT переходит на системный резолвер. Если выбран конкретный поставщик
  (Cloudflare, Google…) — **выключите** или верните «текущего поставщика».
- **Firefox**: по умолчанию DoH выключается канарейкой; если включён вручную («Максимальная защита»
  или `network.trr.mode` 2/3) — выключите или добавьте домены в `network.trr.excluded-domains`.
- Кэш DNS браузера: Windows-кэш сбрасывается при включении и выключении, браузер держит свой ~1 мин.
  Если сайт из списка открывался до включения — перезапустите браузер или
  `chrome://net-internals/#dns` → «Clear host cache».
- QUIC/HTTP3 идёт по тем же маршрутам — особой обработки не нужно.

### IPv6

Туннель только IPv4. «По доменам»: AAAA имён из списков пусты, программы идут по IPv4 в туннель;
IPv6-подсети из списков маршрутизируются в адаптер, где WireGuard их отбрасывает (программы
переходят на IPv4). «Весь трафик»: `::/1` и `8000::/1` в адаптер — IPv6 не уходит мимо, а
отбрасывается.

## Файлы

| Где | Что |
|---|---|
| `C:\Program Files\VK TURN\` | `vkturn.exe`, `vk-turn-proxyd.exe`, `wintun.dll` |
| `%ProgramData%\VK TURN\` (SYSTEM и администраторы) | `settings.json` (ключи, ссылки), `lists\*.srs`, `run\status.json`, `state\creds.json` (кэш кредов), `ui-token`, `ui-users` |
| `%LOCALAPPDATA%\VK TURN\window` | профиль окна Edge |
| реестр | сервис `VKTurn`, `HKLM\SOFTWARE\Classes\vkturn` и `.vkturn`, `HKCU\…\Run\VK TURN` (трей при входе, если включено «подключаться при запуске») |

Демон на Windows сверяет ACL конфига и каталогов статуса и кэша: права на запись (а у конфига — и на
чтение) только у SYSTEM и администраторов (`cmd/vk-turn-proxyd/os_windows.go`) — аналог проверок
0600/0700 на роутере.

## Сборка

```sh
windows/build.sh     # windows/out/vkturn-<ver>-windows-amd64.zip + SHA256SUMS
```

- `vkturn.exe` и `vk-turn-proxyd.exe` — Go хоста, `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 -trimpath
  -mod=readonly`, версия из `windows/VERSION` и коммит.
- `wintun.dll` — единственный бинарник не из этого дерева: официальная подписанная сборка WireGuard
  LLC с wintun.net. Скрипт скачивает `wintun-0.14.1.zip` и сверяет его sha256 с опубликованным на
  wintun.net (`07c25618…ef51`, закреплён в скрипте); если есть `osslsigncode`, показывает подпись DLL.
  Лицензия wintun (разрешает распространять DLL без изменений) кладётся в архив.
- Только x64: ARM64 не собирается (по решению владельца; добавить — `GOARCH=arm64` и
  `wintun/bin/arm64`).

Проверка UI без Windows: `go build -o /tmp/vk-turn-proxyd ./cmd/vk-turn-proxyd && go run ./cmd/vkturn
-demo -daemon /tmp/vk-turn-proxyd` → `http://127.0.0.1:47447/login?t=demo` (сеть фальшивая, демон
без root не стартует — видна ошибка).

## Проверено и не проверено

Проверено на Mac: Go-тесты (разбор `.srs` на сгенерированных фикстурах и вручную на настоящих
списках MetaCubeX; DNS-перехватчик против локальных DNS-серверов; таблица маршрутов и TTL; полный
цикл туннеля с фальшивым демоном и фальшивой платформой; импорт профиля по эталонной ссылке панели;
авторизация окна), сборка и `go vet` под windows/amd64, окно в демо-режиме.

**На Windows ещё не запускалось** — ни сервис, ни wintun, ни iphlpapi, ни NRPT, ни трей. Чек-лист
проверки на настоящем ПК — [docs/windows-testing.md](../docs/windows-testing.md).
